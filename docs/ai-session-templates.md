# AI Session Templates

このファイルは、Perplexity（このチャット）と VS Code の GitHub Copilot / Serena に渡すための、AI セッション運用ルールと再利用テンプレートをまとめたものです。

この文書で扱うもの:

- ユーザー → Perplexity に渡す「次スレ冒頭テンプレ」
- Perplexity がセッション開始時に確認するチェックリスト
- Perplexity → VS Code の GitHub Copilot / Serena に渡す指示文テンプレ
- docs / 実装 / ターミナル運用 / commit 運用の共通ルール

この文書の目的は、毎回同じ前提説明を繰り返さず、現在位置・役割分担・安全策・完了条件を短く正確に共有できるようにすることです。

---

## 1. セッション運用方針

### 1.1 役割分担

- Perplexity（このチャット）の役割:
  - 対象リポジトリ / ブランチ / docs を読み、現在位置の整理を担当する
  - issue / Phase / roadmap / 分割方針をもとに、タスクの切り分けと進め方の整理を行う
  - VS Code 側の GitHub Copilot / Serena に渡すための、調査 / 実装 / docs 更新用の指示文を組み立てる
  - 「変更しない範囲」「完了条件」「不要コード削除・重複回避」などの安全策を明文化する
  - docs を先に整理したい場合は、このチャット側で文案を直接整える

- VS Code の GitHub Copilot / Serena の役割:
  - このチャットから渡された指示文に従って、コード調査 / 実装 / docs 反映 / コミット準備を担当する
  - 2 ファイル以上に波及する変更や、責務境界の追跡が必要な場合は Serena MCP を使って影響範囲確認・差分生成・不要コード整理を行う
  - 軽微な 1 ファイル修正や、要件が十分固まっている変更は通常の Copilot 提案で対応する

### 1.2 Serena を使う基準

- 基本ルールは **「2 ファイル以上に波及しそうなら Serena、1 ファイルだけの軽微修正なら通常の Copilot」**
- ただし 1 ファイルでも、影響範囲が読みにくい場合、参照関係を正確に追いたい場合、既存ルールとの整合確認が重要な場合は Serena を使ってよい
- Serena は「判断コストが高い作業」で優先して使う
- Perplexity は調査・切り分け・方針整理・プロンプト作成を担当し、VS Code の Copilot / Serena は実際の修正・反映・コミット準備を担当する

### 1.3 docs の運用方針

- docs は差分修正前提ではなく、**必要ならフルアップデートしてよい**
- `dev-roadmap` / `contentjs-split-roadmap` / `atv-design` / `ai-session-templates` は、その時点で読んで全体像が分かる状態を優先する
- 古い章立てや重複説明を無理に残さず、必要なら章ごと整理し直す
- ただし docs ごとの役割は崩さない
- docs 更新は、できるだけこのチャット側で文案を先に整えてから VS Code 側へ渡す

### 1.4 作業タイプの分類

セッション開始時に、今回の作業がどの型かを最初に分類する。

- 構造整理
- UI 見た目調整
- 挙動修正
- docs 整備
- commit / push / PR 作成

特に **UI 見た目調整** の場合は、観察対象と非対象責務を先に固定する。

- 観察対象の例:
  - 位置
  - 幅
  - 背景
  - 角丸
  - padding
  - line-height
  - text shadow
- 変更しない責務の例:
  - 表示 / 非表示条件
  - resolver
  - binder
  - observer
  - bootstrap
  - event wiring

また、shell / style 調整タスクでは、`build*ShellHTML()` 側で持つ責務と `create*()` 側で持つ責務を先に分けて考える。

### 1.5 分割作業の前提

- `content.js` の分割は、既存挙動をできるだけ変えずに責務を分けるために行う
- 同時に、コード量を減らし、見通しを良くし、追跡しやすくすることも重要な目的とする
- 一括分割ではなく、Phase 単位で安全に段階分割する
- 純関数・独立責務を先に切り出し、DOM 依存・observer 依存・Apple TV+ 固有 UI 依存が強い層は後ろに回す

### 1.6 VS Code ターミナル運用

- 分割作業や調査は、VS Code ターミナルの `git` / `grep` / `sed` / `node` / `python3` などを使って進める
- 例: `git status` / `git diff --stat` / `grep -n` / `sed -n` / `node --check` を使って、影響範囲確認・抜粋確認・構文確認を行う
- 確認コマンドや更新処理が長くなる場合は、`python3 - <<'PY'` 形式の小さなスクリプトにまとめて実行してよい

### 1.7 基本ルール

- セッション開始時に、対象リポジトリ / ブランチ / 関連 docs / 関連 issue を明示する
- `docs/dev-roadmap.md` と `docs/contentjs-split-roadmap.md` を必要な範囲で読み、現在位置を把握してから作業に入る
- すでに完了している範囲と、今回戻らない範囲（再調査・再実装しないもの）を整理してから進める
- 指示文では「目的」「対象」「変更しない範囲」「完了条件」を明示する
- 変更は最小差分を基本とするが、docs は必要に応じてフルアップデートしてよい
- 既存 helper / 既存フロー / 既存 state を再利用し、別経路のコピペ実装を増やさない
- 同じ責務の処理を分岐ごとに複製しない
- 旧ロジックを残したまま新ロジックを継ぎ足さず、置き換えられるものは置き換える

## 2. このチャット用チェックリスト

セッション開始時に、このチャットが確認すること:

- 対象リポジトリ / ブランチ / 関連 Issue / Phase を確認したか
- `docs/dev-roadmap.md` と `docs/contentjs-split-roadmap.md` を必要な範囲で読み、現在位置を把握したか
- `docs/atv-design.md` を読むべきテーマかどうか判断したか
- すでに完了している範囲と、今回戻らない範囲を整理したか
- 今回の目的を分類したか
  - 調査 / 実装 / docs 整備 / commit / push だけ など
- 今回の作業が、構造整理 / UI 見た目調整 / 挙動修正 のどれに近いか切り分けたか
- UI 見た目調整の場合、観察対象と変更しない責務を先に固定したか
- 触らない責務を把握しているか
- 既存処理へ寄せるべきか、新規追加が本当に必要かを切り分けたか

## 4. 共通ルール（実装・docs 共通）

- 変更は目的に対して最小限に保つ
- docs は必要なら差分修正ではなくフルアップデートしてよい
- 既存 helper / 既存フロー / 既存 state を再利用し、別経路のコピペ実装を増やさない
- 同じ責務の処理を分岐ごとに複製しない
- 今回の issue の責務を超える全面リファクタリングは行わない
- UI 見た目調整では、見た目の変更と挙動変更を同じバッチで混ぜない
- shell / style 調整では、`build*ShellHTML()` と `create*()` の責務を先に切り分ける
- 実装でも docs でも、変更によって不要になった旧記述・旧分岐・未使用変数・死んだ説明は削除候補として確認する

## 5. 実装スレ用進捗メモテンプレ

実装スレでは、セッション冒頭の前提共有だけでなく、**そのスレ内で継続的に更新する進捗メモ**を持つ。  
これは「今回どこまで進んだか」「何を決めたか」「何を次スレへ持ち越すか」を、スレ単位で追跡しやすくするためのテンプレである。

この進捗メモは、Issue の Phase 作業や `content.js` 分割のように、複数セッションにまたがる実装で特に有効。  
Perplexity は、実装スレ開始時に必要ならこのテンプレを提示し、各セッション終了時に更新案をまとめる。

### 5.1 進捗メモの役割

- スレッド内の **ログ兼ナビ** として使う
- 「今回のゴール」「今回決まったこと」「まだ残っていること」をスレ単位で追跡する
- 次スレを立てるときの handoff の元資料にする
- docs 更新や Issue コメント更新が必要かどうかを見落としにくくする

### 5.2 実装スレの進め方

実装スレでは、原則として次の順で進める。

1. **方針相談フェーズ**
   - まず「今回のセッションで何を決めたいか」「今回戻らない範囲はどこか」を相談する
   - 例:
     - A/B/C のどれから試すか
     - 真実源側を触るのか、表示側を触るのか
     - 今回の最小ゴールをどこに置くか
   - このフェーズでは、AI はターミナルコマンドを出さない

2. **確認コマンドフェーズ**
   - 方針が決まってから、その方針に必要な確認だけを行う
   - VS Code ターミナルでは `git` / `grep` / `sed` / `node` / `python3` などを使う
   - 例:
     - `git status`
     - `git diff --stat`
     - `grep -n`
     - `sed -n`
     - `node --check`
   - 何を確認するためのコマンドかを先に言語化してから実行する

3. **実装コマンドフェーズ**
   - 確認結果を踏まえて、編集対象ファイル・編集内容・変更しない範囲を整理し、実装へ進む
   - コマンドは VS Code ターミナルでそのまま貼って実行できる形にする
   - コマンドにはコメント行を含めない

4. **確認・記録フェーズ**
   - 実装後は、差分確認・debug 観測・構文確認などを行い、
     - 何が改善したか
     - 何がまだ残っているか
       を言語化する
   - 結果を進捗メモの `結果まとめ` と `次の TODO` に反映する

### 5.3 実装スレ用進捗メモテンプレ

```markdown
## 今回のゴール

- [ ] 今回のセッションで何を「終わった」とみなすかを 3〜10 項目くらいで書く
- [ ] 真実源側（blocks / sequence）か表示側（panel / overlay / history）か、どこを主に触る回かを明示する
- [ ] 新しく決めたい方針（例: resolver 調整の A/B/C からどれを採るか）をゴールとして書いておく

---

## 実装メモ

- [YYYY-MM-DD hh:mm] セッション #N
  - 検討したこと:
    - 箇条書きで「何について考えたか」を 2〜4 行程度で
  - 実施したこと:
    - 実際にコードを触った内容があればここに列挙
    - ファイル名とやったことが分かる粒度で書く
  - 決めたこと:
    - セッション内で「もう戻さない」レベルで決めた方針を簡潔に
  - 未決事項:
    - 次回以降に持ち越す論点を箇条書きで

※セッションが増えたら、今回スレの範囲だけをざっと追えるように上から時系列で足していく。

---

## 結果まとめ

- 決まったこと:
  - 今回のスレで固めた方針を箇条書きで
  - 真実源モデル / resolver 方針 / current-fallback まわりなど、次スレに持ち越す前提をここで整理しておく
- Phase X-Y の最小実装ライン:
  - 「この Phase ではここまで終わっている」と言える最小ラインを 3〜6 項目くらいで
- 推奨される段階移行:
  - blocks 真実源 → panel → overlay → history のように、「どの順で寄せていくか」を簡潔にまとめる
- まだ残っていること:
  - このスレでは決め切れていない／手を付けていない論点を箇条書きで
- docs 更新が必要か:
  - ~~必要~~ / **対応済み** のように状態を一行で
  - 反映した内容があれば軽く箇条書き
- Issue コメント更新が必要か:
  - ~~必要~~ / **対応済み** で状態を一行で
  - コメント済みなら「何を共有したか」を一行だけ足す

## 設計スレへ相談する場合のルール

- 設計スレへ投げるのは次のような場合に限る:
  - 真実源モデル（blocks / sequence / key / stable）の方針を大きく変えたいとき
  - resolver 層の役割を根本的に変えたいとき
  - panel / overlay / history の責務分担を大きく変えたいとき
  - Phase 境界（Phase 3-1 / 3-2 / 3-3 …）自体の切り方を見直したいとき
- 実装スレで決めるのは次のような粒度:
  - どの案から試すか（A/B/C の優先順）
  - 「このファイルをこう直す」レベルの具体実装
  - debug の出し方やログの粒度
- 設計スレへ相談するときは:
  - 「前提」「現状の実装」「困っているポイント」「相談したい粒度」を短く 4 セクションに分ける
  - 実装寄りに議論したい部分は実装スレに残しておき、設計スレでは方針決定だけに集中する

---

## 次の TODO

- [ ] 次のフェーズ用スレッド（例: `Issue #32 Phase 3-4 / overlay blocks 移行`）のタイトルと冒頭文を決める
- [ ] 次スレの「今回のゴール」を 3〜10 項目で書く
- [ ] `buildSubtitleBlockSequence(now)` の入力・出力 shape が最新の実装と合っているかを確認する
- [ ] resolver に渡す `subtitleBlocks` / `currentIndex` / `meta` の契約を見直し、コメントに残す
- [ ] `current-fallback` に関する調整案（A/B/C）のうち、次に試す案を 1 つ選ぶ
- [ ] 選んだ案の実装対象ファイルと差分の粒度を小さく洗い出す
- [ ] debug パネルで観測する時間帯とログ形式を決める
- [ ] 実装後に確認するシナリオ（例: 32〜40秒帯 / 59〜68秒帯 / 大シーク / reopen）をチェックリストにする
```

### 5.4 補足ルール

- 実装スレでは、**方針相談なしにいきなり確認コマンドへ入らない**
- 確認コマンド → 実装コマンドの順は守るが、その前に必ず方針相談を置く
- コード編集では、ファイル冒頭の概要コメントと、関数や責務の塊ごとの短いコメントを必要最小限で入れる
- すべての変更を「`content.js` を分割し減らす」という Issue の目的に照らして判断する
- 小実験で吸収できない論点は、実装スレだけで抱え込まず設計スレへ戻す
