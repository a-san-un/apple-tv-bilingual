# AI Session Templates

このファイルは、Perplexity（実装スレ）と VS Code ターミナルを中心に進めるための、セッション運用ルールと再利用テンプレートをまとめたものである。

目的は、毎回同じ前提説明を繰り返さず、現在位置・役割分担・安全策・完了条件を短く正確に共有できるようにすること。

---

## 1. 運用原則

### 1.1 役割分担

- **Perplexity（実装スレ）**
  - 対象リポジトリ / ブランチ / docs / issue を読み、現在位置と今回の目的を整理する
  - 方針相談では、変数名や関数名に寄りすぎず、自然な言葉と概念レベルの説明を先に出す
  - 調査 / 実装 / docs 更新に必要な確認コマンド（`python3` を含む）を、VS Code ターミナルでそのまま実行できる形で出す
  - 「変更しない範囲」「完了条件」「不要コード削除・重複回避」などの安全策を明文化する
  - 実装スレ内の進捗メモを更新する（セッション最初の方と、ステップがひと段落ついたタイミングで意識的に出す）
  - 進捗メモの `次の TODO` を定期的に表示し、今どこまで終わっていて次に何をするかを明確にする
  - git のタイミング判断をユーザーが Perplexity に任せている場合、進捗メモと責務完了単位を基準に、早めのステージング / コミット / プッシュを提案する

- **VS Code ターミナル**
  - 実装スレで出した確認コマンド・実装コマンドをそのまま貼って実行する
  - ファイル編集、`git add` / `git commit` / `git push` を行う

- **GitHub Copilot / Serena**
  - 現状は優先度低
  - 複数ファイルへまたがる大きめのリファクタ、または参照関係調査が必要になったタイミングで検討する

### 1.2 docs / 実装の共通ルール

- セッション開始時に、対象リポジトリ / ブランチ / 関連 docs / 関連 issue を明示する
- 今回の作業で正本になる docs を先に確認し、現在位置を把握してから進める
  - 例: Issue #32 の設計・実装スレでは `docs/issue-32-subtitle-sync-design.md` を最優先で読む
- roadmap の再確認が必要な回だけ `docs/dev-roadmap.md` / `docs/contentjs-split-roadmap.md` を読む
- Issue 個別の設計・実装が中心の回では、対応する issue docs を優先する
- すでに完了している範囲と、今回戻らない範囲（再調査・再実装しない部分）を整理してから進める
- 指示や方針では、「目的」「対象」「変更しない範囲」「完了条件」を明示する
- 既存 helper / 既存フロー / 既存 state を再利用し、重複コードを増やさない
- 旧ロジックを残したまま新ロジックを継ぎ足さず、置き換え後の不要コードは削除候補として確認する
- 変更は最小差分を基本とするが、docs は必要に応じてフルアップデートしてよい
- 実装先行で docs と型名・フィールド名がズレた場合は、次スレ冒頭で docs 同期を最優先に置いてよい

### 1.3 作業タイプの分類

セッション開始時に、今回の作業がどの型かを先に分類する。

- 構造整理
- UI 見た目調整
- 挙動修正
- docs 整備
- commit / push / PR 作成

UI 見た目調整では、観察対象と変更しない責務を先に固定する。

- 観察対象の例
  - 位置
  - 幅
  - 背景
  - 角丸
  - padding
  - line-height
  - text shadow
- 変更しない責務の例
  - 表示 / 非表示条件
  - resolver
  - binder
  - observer
  - bootstrap
  - event wiring

shell / style 調整では、`build*ShellHTML()` 側で持つ責務と `create*()` 側で持つ責務を先に分けて考える。

### 1.4 content.js 分割の前提

- `content.js` の分割は、既存挙動をできるだけ変えずに責務を分けるために行う
- 同時に、コード量を減らし、見通しを良くし、追跡しやすくすることも重要な目的とする
- 一括分割ではなく、Phase 単位で安全に段階分割する
- 純関数・独立責務を先に切り出し、DOM 依存・observer 依存・Apple TV+ 固有 UI 依存が強い層は後ろに回す
- subtitle sync / recovery の改善も、`content.js` に状態や分岐を足し続けるのではなく、controller / resolver / helper 側へ責務移送する方針を基本とする

## 2. セッション開始チェック

セッション開始時に、この実装スレで確認すること。

- 対象リポジトリ / ブランチ / 関連 Issue / Phase を把握したか
- 今回の作業で正本となる docs を確認したか
- roadmap 再確認が必要な回か、Issue 個別 docs を優先すべき回かを判断したか
- すでに完了している範囲と、今回戻らない範囲を整理したか
- 今回の目的を分類したか
  - 調査 / 実装 / docs 整備 / commit / push のどれか
- 今回の作業が、構造整理 / UI 見た目調整 / 挙動修正 のどれに近いか切り分けたか
- UI 見た目調整なら、観察対象と変更しない責務を先に固定したか
- 方針相談では、変数名より先に概念レベルの説明を出す形になっているか
- 触らない責務を把握しているか
- 既存処理へ寄せるべきか、新規追加が本当に必要かを切り分けたか
- 進捗メモテンプレを最初から出すべきか、2 投目以降に回すべきかを判断したか
- 今回のセッションで `次の TODO` を定期表示する運用にするか確認したか

## 3. 実装スレの基本フロー

### 3.1 方針相談

- 今回の目的と触る層（truth / resolver / UI）を先に切り分ける
- 変数名・関数名を連呼しすぎず、自然な言葉と概念図で説明してから細部に入る
- 今回戻らない範囲を明示する
- このフェーズではターミナルコマンドを出さない
- 必要なら、方針相談の終わりに進捗メモテンプレと `次の TODO` を先に出してよい

### 3.2 確認コマンド

- 方針に必要な範囲だけ `git` / `rg` / `grep` / `sed` / `node --check` / `python3` 等で確認する
- 何を確認するためのコマンドかを先に言語化してから出す
- コマンドは VS Code ターミナルでそのまま貼って実行できる形にする
- **確認コマンドはコメント行（`# ...`）を含めない**
- 同じ確認フェーズ内では、なるべく 1 つのコードブロックにまとめて出す（`&& \` で連結してもよい）
- 確認結果を受けたら、すぐ次の確認を積み増すのではなく、いったん「何が確認できて、何が未確認か」を言語化する

### 3.3 実装

- 編集対象ファイルと変更内容を列挙してから実装へ進む
- 変更しない範囲もセットで確認する
- コマンドを出す場合は、`python3 - <<'PY'` なども含めてそのまま使える形にする
- 実装に入る前に、進捗メモの `次の TODO` を更新してから進んでもよい

### 3.4 テスト・記録

- 実装後は、動作確認・debug 観測・差分確認・構文確認を行う
- 少なくとも次を言語化する
  - 何が改善したか
  - 何がまだ残っているか
- 結果は進捗メモの `結果まとめ` と `次の TODO` に反映する
- 進捗メモは、セッション最初の方と、ステップがひと段落ついたタイミングで更新する
- 長いセッションでは、`次の TODO` だけを抜粋して再表示してよい

### 3.5 ステージング / コミット / プッシュ

- **方針相談 → 確認 → 実装 → テスト** が一まとまり終わったところで、ステージング / コミット / プッシュを検討する
- Perplexity は、次のようなタイミングで **こまめに git 操作を提案する**
  - 1 つの責務単位の変更が完了したとき（関数単位・セクション単位などの小さなまとまり）
  - docs とコードの同期が 1 セット終わったとき
  - 進捗メモ上の「今回のゴール」の 1 項目が達成されたとき
  - Issue / docs 更新だけが先に完了し、他の未整理差分と混ざる前に分けてコミットしたほうがよいとき
- git 操作の基本パターン
  - 差分確認: `git status` / `git diff --stat`
  - 必要なら対象限定の差分確認: `git diff path/to/file`
  - ステージング: `git add path/to/file`
  - コミット: Issue / Phase が分かるメッセージを、3.6 のルールに沿って提案する
  - プッシュ: 必要なら `git push origin <branch>` まで進める
- コミット単位は「意味のある小さなステップ」を基本とし、
  長時間にわたる変更を 1 コミットへまとめず、こまめにコミットする
- ユーザーが git のタイミング判断を Perplexity に任せている場合、Perplexity は
  「今はまだコミットしない」か「ここでコミットする」かを定期的に言語化する

### 3.6 コミットメッセージルール

- 形式は **プレフィックス（英語）+ 本文（日本語）** とする
  - `feat: ...` 新機能・UI 追加
  - `fix: ...` バグ修正・挙動修正
  - `refactor: ...` 構造整理・責務分割
  - `docs: ...` docs 更新のみ
  - `chore: ...` 雑多な変更・観測用追加
- 1 行目は「このコミットで何をしたか」がざっくり分かればよい
  - 例: `fix: large seek 後のサブ字幕復帰を安定させる (Issue #32, Phase J)`
- 詳細を書きたいときだけ、**箇条書きをゆるく追加する**
  - すべてのコミットで必須ではない
  - 「どのファイルに何をしたか」が分かる程度でよい

例（詳細あり）:

```txt
chore: secondary recovery 観測と resolver probe を追加する

- content.js に secondaryRecoveryMissCount と getMergedSubtitleHealthSnapshot() を追加した
- cue-controller.js に lastMergedSubtitleHealth と getMergedSubtitleHealth() を追加した
- subtitle-track-resolver.js に getSecondarySubtitleTrackCandidates() を追加した
```

例（もっとラフな書き方）:

```txt
fix: secondary runtime recovery 条件を Phase J 仕様に揃える (Issue #32)

- cue-controller.js の runtime 条件と recovery window を docs 通りにした
```

- 箇条書きは「1〜3 行くらい」で十分
- 負荷が高いときは **1 行目だけ**でもよい（詳細は Issue / docs /進捗メモに書く）

## 4. 進捗メモテンプレ

```md
## 今回のゴール

- [ ] 今回のセッションで何を「終わった」とみなすかを 3〜10 項目くらいで書く
- [ ] 真実源側（blocks / sequence）か表示側（panel / overlay / history）か、どこを主に触る回かを明示する
- [ ] 新しく決めたい方針（例: resolver 調整の A/B/C からどれを採るか）をゴールとして書いておく

---

## 実装メモ

- [YYYY-MM-DD] セッション #N
  - 検討したこと:
    - 箇条書きで 2〜4 行程度
  - 実施したこと:
    - ファイル名とやったことが分かる粒度で書く
  - 決めたこと:
    - セッション内で「もう戻さない」レベルで決めた方針を簡潔に
  - 未決事項:
    - 次回以降に持ち越す論点を箇条書きで

---

## 結果まとめ

- 決まったこと:
  - 今回のスレで固めた方針を箇条書きで
- Phase X-Y の最小実装ライン:
  - 「この Phase ではここまで終わっている」と言える最小ラインを 3〜6 項目くらいで
- 推奨される段階移行:
  - どの順で寄せていくかを簡潔にまとめる
- まだ残っていること:
  - このスレでは決め切れていない / 手を付けていない論点を箇条書きで
- docs 更新が必要か:
  - ~~必要~~ / **対応済み**
- Issue コメント更新が必要か:
  - ~~必要~~ / **対応済み**

---

## 次の TODO

- [ ] 次スレのタイトルと冒頭文を決める
- [ ] 次スレの「今回のゴール」を 3〜10 項目で書く
- [ ] 次に触るファイルと最小差分を洗い出す
- [ ] 実装後に確認するシナリオをチェックリストにする
```

### 4.1 進捗メモ運用の補足

- 進捗メモは、セッション最初の方で 1 回出す
- その後は、確認フェーズ完了時・実装ひと区切り時・docs 更新完了時など、ステップがひと段落ついたタイミングで更新する
- 長いセッションでは、全文を毎回貼り直さず、`次の TODO` だけを短く再表示してよい
- 「今どこまで終わったか」は `結果まとめ` と `次の TODO` の組み合わせで把握する
- 必要なら `今回のゴール` と `次の TODO` の更新で代替する
- Perplexity は、進捗メモの `今回のゴール` のチェックが 1 つ埋まった時点で、その変更が 1 コミット 1 責務として切り出せるかを確認し、切り出せるなら git 操作を提案する

## 5. テスト手順テンプレ

```md
### Phase X / テスト手順

#### 1. テスト項目名

- 手順:
- パネルで見ること:
- オーバーレイで見ること:
- ログで見ること:
- ログフィルター:

#### 2. テスト項目名

- 手順:
- パネルで見ること:
- オーバーレイで見ること:
- ログで見ること:
- ログフィルター:
```

### 5.1 テスト手順を書くときの補足

- 何を操作するかだけでなく、字幕パネル / オーバーレイ / デバッグログのどこを見るかを書く
- デバッグログは、各テストケースの開始前にクリアする前提で書く
- ログフィルターがある場合は、コピーしやすい短い文字列を 1 つずつ出す
- recovery という言葉を使う場合は、「副字幕トラックの再同期・再接続を試す処理」など自然な言葉で補足する

### 5.2 推奨テスト項目名

- `large seek（seekbar 大ジャンプ）`
- `same-window（panel 内 block click を含む近距離移動）`
- `10秒送り戻し（再生コントロールボタン）`
- `panel list / history（通常再生での履歴・current block health）`

## 6. テスト結果メモテンプレ

```md
### Phase X / テスト結果メモ（簡易）

#### 1. テスト項目名

- 操作:
- パネルで見えたこと:
- オーバーレイで見えたこと:
- ログで見えたこと:
- 一言まとめ:

#### 2. テスト項目名

- 操作:
- パネルで見えたこと:
- オーバーレイで見えたこと:
- ログで見えたこと:
- 一言まとめ:
```

### 6.1 ログ記録の補足

- ログ欄には、必要なら「フィルター名」と「代表ログ数行」だけ貼る
- 長いログを貼る場合は、まず一言で要点を書く
  - 例: `secondary recovery が missCount を増やしながら継続し、副字幕は復活しなかった`
- `なし` と書くときは、「ログ自体が出ていない」のか「フィルターに一致しなかった」のかを必要に応じて補足する

## 7. 設計スレへ戻す条件

次のような場合は、実装スレだけで抱え込まず設計スレへ戻す。

- 真実源モデル（blocks / sequence / key / stable）の方針を大きく変えたい
- resolver 層の役割を根本的に変えたい
- panel / overlay / history の責務分担を大きく変えたい
- Phase 境界自体の切り方を見直したい

実装スレで決める粒度は次を基本とする。

- どの案から試すか（A/B/C の優先順）
- 「このファイルをこう直す」レベルの具体実装
- debug の出し方やログの粒度
- 既存設計の範囲内での retry / health / recovery の運用方針

設計スレへ相談するときは、少なくとも次の 4 点を短く分けて書く。

- 前提
- 現状の実装
- 困っているポイント
- 相談したい粒度

## 8. Copilot / Serena を使う場合の補足

- 2 ファイル以上に波及する変更や、責務境界の追跡が必要な場合に検討する
- 使う場合は、この実装スレから次をまとめて VS Code 側へ渡す
  - 対象ファイル
  - 責務境界
  - 変更しない範囲
- 現状の運用では、Perplexity → VS Code ターミナルのコマンド出力で十分なため、Copilot / Serena は必須ではない
