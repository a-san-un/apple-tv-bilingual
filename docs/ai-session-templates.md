# AI Session Templates

このファイルは、Perplexity（この実装スレ）と VS Code ターミナルを中心に進めるための、セッション運用ルールと再利用テンプレートをまとめたものです。

目的は、毎回同じ前提説明を繰り返さず、現在位置・役割分担・安全策・完了条件を短く正確に共有できるようにすることです。

---

## 1. 運用原則

### 1.1 役割分担（現状）

- **Perplexity（実装スレ）**
  - 対象リポジトリ / ブランチ / docs / issue を読み、現在位置と今回の目的を整理する
  - 方針相談フェーズでは、変数名や関数名に寄り過ぎず、自然な言葉と概念図で説明する
  - 調査 / 実装 / docs 更新に必要な確認コマンド（`python3` を含む）をコードブロックで出力する
  - 「変更しない範囲」「完了条件」「不要コード削除・重複回避」などの安全策を明文化する
  - 実装スレ内の進捗メモを更新する

- **VS Code ターミナル**
  - 実装スレで出した確認コマンド・実装コマンドをそのまま貼って実行する
  - ファイル編集や `git add` / `git commit` / `git push` を行う

- **GitHub Copilot / Serena**
  - 現状は優先度低。複数ファイルへまたがる大きめのリファクタや参照関係調査が必要になったタイミングで検討する

### 1.2 docs / 実装の共通ルール

- セッション開始時に、対象リポジトリ / ブランチ / 関連 docs / 関連 issue を明示してもらう
- 今回の作業で正本になる docs を先に確認し、現在位置を把握してから進める
  - 例: Issue #32 の設計・実装スレでは `docs/issue-32-subtitle-sync-design.md` を最優先で読む
- roadmap 再確認が必要な回だけ `docs/dev-roadmap.md` / `docs/contentjs-split-roadmap.md` を読む
- Issue 個別の設計・実装が中心の回では、対応する issue docs を優先して読む
- すでに完了している範囲と、今回戻らない範囲（再調査・再実装しない部分）を整理してから進める
- 指示や方針では「目的」「対象」「変更しない範囲」「完了条件」を明示する
- 既存 helper / 既存フロー / 既存 state を再利用し、重複コードを増やさない
- 旧ロジックを残したまま新ロジックを継ぎ足さず、置き換え後の不要コードは削除候補として確認する
- 変更は最小差分を基本とするが、docs は必要に応じてフルアップデートしてよい
- 実装先行で docs と型名・フィールド名がズレた場合は、次スレ冒頭で docs 同期を最優先に置いてよい

### 1.3 作業タイプの分類

セッション開始時に、今回の作業がどの型かを先に分類する。

- 構造整理
- UI 見た目調整
- 挙動修正
- docs 整備
- commit / push / PR 作成

UI 見た目調整では、観察対象と変更しない責務を先に固定する。

- 観察対象の例:
  - 位置
  - 幅
  - 背景
  - 角丸
  - padding
  - line-height
  - text shadow
- 変更しない責務の例:
  - 表示 / 非表示条件
  - resolver
  - binder
  - observer
  - bootstrap
  - event wiring

shell / style 調整では、`build*ShellHTML()` 側で持つ責務と `create*()` 側で持つ責務を先に分けて考える。

### 1.4 content.js 分割の前提

- `content.js` の分割は、既存挙動をできるだけ変えずに責務を分けるために行う
- 同時に、コード量を減らし、見通しを良くし、追跡しやすくすることも重要な目的とする
- 一括分割ではなく、Phase 単位で安全に段階分割する
- 純関数・独立責務を先に切り出し、DOM 依存・observer 依存・Apple TV+ 固有 UI 依存が強い層は後ろに回す

## 2. この実装スレ用チェックリスト

セッション開始時に、この実装スレ（Perplexity）が確認すること:

- 対象リポジトリ / ブランチ / 関連 Issue / Phase を把握したか
- 今回の作業で正本となる docs（例: issue 個別 docs）を確認したか
- roadmap 再確認が必要な回か、Issue 個別 docs を優先すべき回かを判断したか
- すでに完了している範囲と、今回戻らない範囲を整理したか
- 今回の目的を分類したか
  - 調査 / 実装 / docs 整備 / commit / push だけ など
- 今回の作業が、構造整理 / UI 見た目調整 / 挙動修正 のどれに近いか切り分けたか
- UI 見た目調整の場合、観察対象と変更しない責務を先に固定したか
- 方針相談では、変数名より先に概念レベルの図や自然な説明を出してから細部に入る形にするか
- 触らない責務を把握しているか
- 既存処理へ寄せるべきか、新規追加が本当に必要かを切り分けたか
- 実装スレの場合、進捗メモテンプレを冒頭ではなく 2 投目以降に提示した方がよいか判断したか

## 3. 実装スレの基本フロー

実装スレでは、原則として次の順で進める。

### 3.1 方針相談フェーズ

- 今回の目的と触る層（truth / resolver / UI）を先に切り分ける
- 変数名・関数名を連呼しすぎず、自然な言葉とざっくり概念図で説明してから細部に入る
- 今回戻らない範囲を明示する
- このフェーズではターミナルコマンドを出さない

### 3.2 確認コマンドフェーズ

- 方針に必要な範囲だけ `git` / `rg` / `grep` / `sed` / `node --check` / `python3` 等で確認する
- 何を確認するためのコマンドかを先に言語化してから出す
- コマンドは VS Code ターミナルでそのまま貼って実行できる形にする

### 3.3 実装フェーズ

- 編集対象ファイルと変更内容を列挙してから実装へ進む
- 変更しない範囲もセットで確認する
- コマンドを出す場合は、`python3 - <<'PY'` なども含めて VS Code ターミナルでそのまま貼って使える形にする
- コマンドにはコメント行を含めない

### 3.4 テスト・記録フェーズ

- 実装後は、動作確認・debug 観測・差分確認・構文確認を行う
- 少なくとも次を言語化する
  - 何が改善したか
  - 何がまだ残っているか
- 結果は進捗メモの `結果まとめ` と `次の TODO` に反映する

### 3.5 ステージング / コミット / プッシュ

- 実装スレでは、**方針相談 → 確認 → 実装 → テスト** が一まとまり終わったところで、ステージング / コミット / プッシュを検討する
- Perplexity は、次のようなタイミングで git 操作を指示してよい
  - 1 つの責務単位の変更が完了したとき
  - docs とコードの同期が 1 セット終わったとき
  - 進捗メモ上の「今回のゴール」の 1 項目が達成されたとき
- git 操作の基本パターン:
  - 差分確認: `git status` / `git diff --stat`
  - ステージング: `git add path/to/file`
  - コミット: Issue / Phase が分かるメッセージを提案する
  - プッシュ: 必要なら `git push origin <branch>` まで進める
- コミット単位は「意味のある 1 ステップ」を基本とし、大きい変更を雑に 1 コミットへまとめない

## 4. 実装スレ用進捗メモテンプレ

```markdown
## 今回のゴール

- [ ] 今回のセッションで何を「終わった」とみなすかを 3〜10 項目くらいで書く
- [ ] 真実源側（blocks / sequence）か表示側（panel / overlay / history）か、どこを主に触る回かを明示する
- [ ] 新しく決めたい方針（例: resolver 調整の A/B/C からどれを採るか）をゴールとして書いておく

---

## 実装メモ

- [YYYY-MM-DD hh:mm] セッション #N
  - 検討したこと:
    - 箇条書きで 2〜4 行程度
  - 実施したこと:
    - ファイル名とやったことが分かる粒度で書く
  - 決めたこと:
    - セッション内で「もう戻さない」レベルで決めた方針を簡潔に
  - 未決事項:
    - 次回以降に持ち越す論点を箇条書きで

---

## 結果まとめ

- 決まったこと:
  - 今回のスレで固めた方針を箇条書きで
- Phase X-Y の最小実装ライン:
  - 「この Phase ではここまで終わっている」と言える最小ラインを 3〜6 項目くらいで
- 推奨される段階移行:
  - どの順で寄せていくかを簡潔にまとめる
- まだ残っていること:
  - このスレでは決め切れていない／手を付けていない論点を箇条書きで
- docs 更新が必要か:
  - ~~必要~~ / **対応済み**
- Issue コメント更新が必要か:
  - ~~必要~~ / **対応済み**

---

## 次の TODO

- [ ] 次スレのタイトルと冒頭文を決める
- [ ] 次スレの「今回のゴール」を 3〜10 項目で書く
- [ ] 次に触るファイルと最小差分を洗い出す
- [ ] 実装後に確認するシナリオをチェックリストにする
```

## 5. 設計スレへ戻す条件

次のような場合は、実装スレだけで抱え込まず設計スレへ戻す。

- 真実源モデル（blocks / sequence / key / stable）の方針を大きく変えたい
- resolver 層の役割を根本的に変えたい
- panel / overlay / history の責務分担を大きく変えたい
- Phase 境界自体の切り方を見直したい

実装スレで決める粒度は次を基本とする。

- どの案から試すか（A/B/C の優先順）
- 「このファイルをこう直す」レベルの具体実装
- debug の出し方やログの粒度

設計スレへ相談するときは、少なくとも次の 4 点を短く分けて書く。

- 前提
- 現状の実装
- 困っているポイント
- 相談したい粒度

## 6. Copilot / Serena を使う場合の補足（今は優先度低）

- 2 ファイル以上に波及する変更や、責務境界の追跡が必要な場合に検討する
- 使う場合は、この実装スレから
  - 対象ファイル
  - 責務境界
  - 変更しない範囲
    をまとめた指示文を VS Code 側へ渡す
- 現状の運用では、Perplexity → VS Code ターミナルのコマンド出力で十分なため、Copilot / Serena は必須ではない
