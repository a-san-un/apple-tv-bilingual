# 字幕同期・切り替え条件統合と責務再設計メモ

## 背景

Apple TV+ 上で、拡張機能の字幕言語切り替えは成功する場合と失敗する場合がある。  
この問題は単なる言語一致や DOM セレクタの問題ではなく、**primary / secondary の字幕同期、selection、bind、monitor、recovery、native fallback の判断が複数層に分散していること**に起因している。

既存整理では、secondary の selection / bind / monitor / recovery 条件が複数モジュールへ分散していること、また subtitle decision を集約し execution 側を薄くする方向がすでに見えている。  
一方で、字幕言語切り替え不安定化の調査では、`TextTrack` 直接切り替えと native menu fallback の二重経路、および native UI 依存の不安定さが問題として整理されている。

本メモでは、それらを個別問題としてではなく、**字幕切り替えと playback session lifecycle を同時に扱う統合設計**として再整理する。  
特に、今回の再設計では「どこで切り替えを判断するか」に加えて、「どこが session の owner なのか」を明確にすることを主眼に置く。

***

## 問題の本質

### 1. 切り替え経路が複数ある

字幕言語切り替えには、少なくとも次の 2 経路がある。

#### `TextTrack` 直接切り替え

resolver が `textTracks` を走査し、requested language に合う track を選び、`mode = "showing"` にする経路である。

#### native menu fallback

`TextTrack` 側で cue が読めないときに、Apple TV+ の native 字幕メニューを開き、`select` や option を操作して切り替えを促す経路である。

このため、見た目には同じ「字幕切り替え」でも、実際には別経路の成功・失敗が混在する。  
さらに、切り替え失敗時に「track 選択失敗」「track は選べたが readable にならない」「fallback 実行自体が崩れる」という別種の問題が同じ現象に見えやすい。

### 2. `showing` と readable は別である

現状実装でも、track の評価は単に `mode` ではなく、`cuesLength`、`activeCuesLength`、current cue text、cue overlap、readability snapshot などの情報を見ている。  
つまり実装自身がすでに **「選択されたこと」と「読めること」は別問題**だと扱っている。

このため、成功パターンは「選択後すぐ readable になるケース」、失敗パターンは「`showing` にはなったが cue が来ず、その後 fallback 成否に依存するケース」である。  
ここを曖昧にしたまま `mode` や language 一致だけで成功判定すると、切り替え結果の観測と実装判断が食い違いやすくなる。

### 3. 条件判断が分散している

問題を複雑にしている本質は、切り替え経路が 2 つあること以上に、**その判断材料が複数モジュールへ分散していること**である。

少なくとも次の材料が存在する。

- track が見つかったか。
- その track が readable か。
- 前回 bind と同じ track か。
- requested language が変わったか。
- monitor が健全か。
- force rebind 要求があるか。
- recovery が `recover` / `force-rebind` を要求しているか。
- native fallback を打つべきか。

これらを複数層が別々に解釈すると、同じ現象でも毎回違う経路に入りやすくなり、不安定化する。  
その結果、selection、monitor、recovery、fallback がそれぞれ独自に「今は rebind すべき」と判断し、session の状態が局所的にねじれやすくなる。

***

## 現象整理

### なぜ成功パターンと失敗パターンが分かれるのか

#### 成功しやすいパターン

- requested language に一致する track がすぐ見つかる。
- `TextTrack` を `showing` にした直後または短時間待機後に cue が読める。
- 前回 binding と大きな矛盾がない。
- monitor が健全である。
- native fallback を打たなくても十分動く。

#### 失敗しやすいパターン

- requested language には合っているように見えるが cue が来ない。
- `showing` にはなったが `cuesLength === 0` が続く。
- native menu を開いても `menuRoot` / `select` / option 発見に失敗する。
- UI 文言や DOM 構造変更で option 一致判定が外れる。
- seek / reattach / scene 切り替えと fallback 実行タイミングが競合する。
- monitor / recovery / binder / controller が別々に再bind判断を行う。

#### 要点

成功・失敗の差は、単なる「言語一致判定の精度差」ではなく、**selection・readability・monitor・recovery・native fallback の解釈が一元化されていないこと**にある。

***

## 統合の基本方針

### 方針

**selection result ではなく decision result を単一箇所で返す構成**へ寄せる。

流れは次のように整理する。

1. `track` と `snapshot` を選ぶ。
2. 前回 binding 状態と monitor 状態を受け取る。
3. recovery 要求を受け取る。
4. derived condition を一箇所で作る。
5. 最終 action を返す。
6. 実行側は action 実行だけを担当する。

要点は、**「何をすべきか」を一箇所が返し、他はそれを実行するだけに寄せる**ことにある。  
ただし、今回の再設計ではこの考え方を字幕同期だけに閉じず、playback session 全体の owner 設計にも拡張する。

***

## 今回追加する設計原則

### 1 playback target = 1 playback session

今回の責務再設計では、まず **1 playback target = 1 playback session** と定義する。  
動画要素、textTracks listener、MutationObserver、poll/timeout、secondary subtitle DOM、panel UI、debug panel runtime、各種 dispose 関数群は、その session の所有物として扱う。

この定義を置く理由は、字幕切り替え不安定化の原因が「字幕 decision の分散」だけではなく、「起動・再起動・UI 再マウント・cleanup の owner が複数あること」にもあるからである。  
同じ playback target に対して複数層が独自に起動や teardown を触ると、メモリーリークというより **stale な半死状態 session** が残りやすくなる。

### 1 session 1 owner

1 つの playback session には、最終的に 1 人の owner しか存在してはいけない。  
settings、reinitialize、panel、debug、subtitle sync の各層は session に関与してもよいが、session の生殺与奪を握る owner は単一であるべきである。

この owner は、起動前段の統制、session 開始、session 終了の交通整理を一貫して扱える必要がある。  
そのため、session lifecycle は「どこから start されたか」ではなく、「必ず同じ入口と同じ終了口を通るか」で設計すべきである。

### 単一路線

最終的に寄せたい流れは次の一本である。

target change / settings changed / track invalidation  
→ coordinator が再評価する  
→ 必要なら current session を cleanup する  
→ coordinator が新しい target に attach する  
→ start 本体が session を構築する

この形にすると、どのイベントから入っても rebuild の読み方が変わらない。  
また、start、retry、cleanup、UI dispose の責務が分かれ、ログ観測でも一筆書きで経路を追いやすくなる。

***

## owner 構成の再定義

### `playback-startup-coordinator`

`playback-startup-coordinator` は、起動そのものを全部やる場所ではなく、**起動前段の coordination と playback target change の監視を担う owner 前段**として扱う。  
ここには playback target 変化検知、startup readiness 判定、readiness 待ち、delayed retry、起動 attempt の再入防止を集約する。

つまり、このモジュールの責務は「いつ start すべきかを決めること」であり、「字幕同期をどう bind するか」や「UI をどう描画するか」ではない。  
settings や reinitialize からの要求はここに集め、ここ以外が直接 start owner にならない構成を目指す。

### `startBilingual(...)`

`startBilingual(...)` は、実際の session 構築本体である。  
tracks 解決、listener 接続、secondary DOM 構築、panel UI 初期化、debug panel runtime 初期化など、**その session を動かすために必要な所有物を作ること**に責務を絞る。

ここでは readiness 判定や再起動判断まで抱え込まない。  
「起動してよいか」は coordinator が決め、「何を作るか」は `startBilingual(...)` が引き受ける形にすると、コードが短くなり責務も読みやすくなる。

### `playback-session-cleanup`

`playback-session-cleanup` は、**再生 session 単位の teardown と再入ガードの唯一入口**として扱う。  
observer、listener、timer、secondary subtitle DOM、panel UI、debug panel runtime、購読解除、snapshot reset など、session 所有物の解放をここに集約する。

重要なのは、cleanup を「必要に応じてどこかが少しずつやる」構造にしないことである。  
session cleanup の正本 API をひとつ持ち、どこからの rebuild 要求でも必ずそこを通して古い session を落とす。

### `settings-runtime`

`settings-runtime` は、保存設定の読込、runtime state 反映、必要時の再評価依頼だけに縮退する。  
ここが直接 `startBilingual()` を呼ぶ、独自に `textTracks` の readiness を待つ、`addtrack` listener / poll / timeout を所有する、といった構成は持たない方向へ寄せる。

設定変更時に必要なのは「自分で start すること」ではなく、「coordinator に再評価してもらうこと」である。  
これにより settings 層は session owner ではなくなり、runtime state と lifecycle state の境界がはっきりする。

### `reinitialize-coordinator`

`reinitialize-coordinator` は、「なぜ再起動が必要か」を判定して要求を発行する薄い層へ縮退する。  
実 cleanup や内部 state の大規模初期化、再接続の実作業まで持つと、cleanup 層や start 本体と責務が競合する。

そのため、この層は reason 判定と rebuild request に寄せる。  
実際の teardown は `playback-session-cleanup`、実際の再構築は coordinator と `startBilingual(...)` に流すのが自然である。

### `panel-ui` と `debug-panel-runtime`

panel UI と debug panel runtime は、「ユーザーが開閉するので独立 owner を持つ UI」ではなく、**session 従属 UI** として扱う。  
session 開始時に mount し、session cleanup 時に dispose するのが基本である。

この考え方に立つと、`panelUi.dispose()` や debug runtime の購読解除は「個別 UI の都合」ではなく、「session teardown の一部」として理解できる。  
結果として、UI だけ古い session にぶら下がる状態を防ぎやすくなる。

***

## decision result と session owner の関係

既存の decision result 正本化は、字幕 lane の判断を一箇所に寄せる考え方として有効である。  
ただし、字幕 decision がきれいでも、session lifecycle の owner が複数あると、最終的な不安定さは残りやすい。

そのため、今回の再設計では二段構えで考える。

- 字幕切り替え条件は decision result で一元化する。
- playback session lifecycle は single owner 構成で一元化する。

前者は「何をするか」の統一であり、後者は「誰がそれを始めて終わらせるか」の統一である。  
この 2 つが揃ってはじめて、selection・monitor・recovery・native fallback の複雑さを実装上も説明できるようになる。

***

## decision result の正本化

### 中心オブジェクト案

```js
{
  role, // "primary" | "secondary"

  track,
  currentTime,
  snapshot,

  previous: {
    boundTrack,
    boundTrackId,
    requestedLang,
  },

  selection: {
    resolvedTrack,
    selectedTrackId,
    sameTrackRef,
    requestedLanguageChanged,
  },

  monitor: {
    active,
    hasCleanup,
    track,
    sameTrack,
    sameMode,
    healthy,
    stale,
  },

  recovery: {
    requested: false,
    forceRebind: false,
    terminated: false,
    reason: "",
  },

  derived: {
    trackFound,
    readable,
    shouldClear,
    needsReadableWait,
    needsRebind,
    canKeepCurrentBinding,
    needsNativeSelectionFallback,
  },

  action: {
    type:
      "clear" |
      "keep" |
      "wait-and-bind" |
      "bind" |
      "native-fallback-and-wait",
    reason: "",
    requestedMode: "hidden",
  }
}
```

### この形にする意図

- `selection` は「何を選んだか」である。
- `monitor` は「今の binding が健全か」である。
- `recovery` は「時間軸観測上、昇格要求があるか」である。
- `derived` は「現在状態をどう解釈したか」である。
- `action` は「最終的に何をするか」である。

これにより、条件の意味とログの意味が分離され、調査しやすくなる。  
また、session owner 側から見ても「字幕 lane 側が今どういう理由で bind / wait / clear を返したか」が読みやすくなる。

***

## action の再定義

### 既存 action

#### `clear`

対象 lane 用 track が存在しない、または表示を継続すべきでないとき。

#### `keep`

今の binding をそのまま維持してよいとき。

#### `wait-and-bind`

track はあるが readable でない、または warmup を入れたいとき。

#### `bind`

即 bind してよいとき。

#### `native-fallback-and-wait`

`TextTrack` 側だけでは十分でなく、native menu fallback を打ってから待機すべきときである。

### action 解釈の補足

重要なのは、これらの action を lane 単位 decision として扱い、session lifecycle の start / cleanup と混同しないことである。  
たとえば `wait-and-bind` は lane の bind 戦略であって、session 全体を再生成する命令ではない。

逆に、session owner 側が target 変化や settings 変更を検知したときは、lane action の前に session の rebuild 必要性を判断する。  
この順番を守ることで、「lane の bind 失敗を session 再構築でごまかす」「session rebuild が必要なのに lane action だけで延命する」といった責務の混線を防げる。

## 実装修正の方向

### 単一路線へ寄せる

いまのコードベースは、すでに `playback-startup-coordinator`、`playback-session-cleanup`、`settings-runtime`、`reinitialize-coordinator` に責務を分け始めている。  
そのため、全面的な作り直しではなく、**起動・再起動・UI 再マウントの入口を一本化し、1 session 1 owner に寄せる**のが最も効果的である。

最初にやるべきことは、`settings-runtime` から直接起動経路を外すことである。  
次に、`reinitialize-coordinator` を判定要求層へ縮退し、`playback-session-cleanup` に teardown を集約する。

最後に、panel / debug panel / secondary DOM を session 従属 UI として cleanup 配下へ完全に寄せる。  
ここまで揃うと、settings changed、target change、track invalidation のどこから入っても、同じ rebuild 経路で説明できるようになる。

### 最終的に目指す流れ

最終形のイメージは次のとおりである。

- target change / settings changed / track invalidation が起きる。
- `settings-runtime` または `reinitialize-coordinator` が再評価を依頼する。
- `playback-startup-coordinator` が rebuild 必要性を判断する。
- 必要なら `playback-session-cleanup` が current session を dispose する。
- `playback-startup-coordinator` が新しい target に attach する。
- `startBilingual(...)` が新しい session を構築する。

この流れに寄せる目的は、処理を増やすことではなく、**同じ種類の責務を同じ場所へ集めてコードを短くすること**にある。  
複数箇所にある start、retry、cleanup、UI 再接続を一本に寄せるほど、ファイル数はそのままでも各ファイルの意味は明確になる。

***

## このメモで固定したいこと

本メモでは、次の設計原則を正本として扱う。

- 字幕切り替えの lane decision は decision result を単一箇所で返す。
- 1 playback target = 1 playback session とみなす。
- 1 playback session には 1 owner だけを持たせる。
- 起動前段の統制は `playback-startup-coordinator` に寄せる。
- 実 session 構築は `startBilingual(...)` に寄せる。
- session teardown は `playback-session-cleanup` に寄せる。
- `settings-runtime` は state 反映と再評価依頼に縮退する。
- `reinitialize-coordinator` は再起動理由判定と要求発行に縮退する。
- panel UI と debug panel runtime は session 従属 UI として扱う。

この設計により、字幕同期と playback lifecycle を別問題としてではなく、**判断の一元化と owner の一元化**という 2 軸で整理できる。  
以後の実装整理では、この原則に従って「残す責務」「移す責務」「消す経路」を各ファイルに割り当てる。
