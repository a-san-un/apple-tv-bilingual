# 字幕同期・切り替え条件統合と責務再設計メモ

## 背景

Apple TV+ 上で、拡張機能の字幕言語切り替えは成功する場合と失敗する場合がある。
この問題は単なる言語一致や DOM セレクタの問題ではなく、**primary / secondary の字幕同期、selection、bind、monitor、recovery、native fallback の判断が複数層に分散していること**に起因している。

既存の `Secondary 条件統合メモ.md` では、secondary の selection / bind / monitor / recovery 条件が次のモジュールへ分散していると整理されている。

- `subtitle-sync-controller.js`
- `cue-controller.js`
- `cue-track-binder.js`
- `subtitle-recovery-manager.js`
- `secondary-track-recovery.js`

また、`Secondary 統合後の責務再定義一覧.md` では、secondary decision を `subtitle-sync-controller.js` へ集約し、`cue-controller.js` を実行・交通整理役へ薄くする責務分割が提案されている。

一方、`字幕言語切り替え不安定化の調査・修正方針.md` では、字幕言語切り替えが不安定になる理由として、`TextTrack` 直接切り替えと native menu fallback の二重経路、および native UI 依存の不安定さが整理されている。

これら 3 文書は現在 separate だが、実際には次の一つの問題を別角度から見ている。

- 字幕切り替えがなぜ不安定なのか
- その条件をどこで判断すべきか
- 各モジュールの責務をどう再設計すべきか

そのため、本メモでは **primary / secondary 両 lane を含む統合設計メモ**として再整理する。

***

## 問題の本質

## 1. 切り替え経路が複数ある

字幕言語切り替えには、少なくとも次の 2 経路がある。

### `TextTrack` 直接切り替え

resolver が `textTracks` を走査し、requested language に合う track を選び、`mode = "showing"` にする経路。

### native menu fallback

`TextTrack` 側で cue が読めないときに、Apple TV+ の native 字幕メニューを開き、`select` や option を操作して切り替えを促す経路。

このため、見た目には同じ「字幕切り替え」でも、実際には別経路の成功・失敗が混在する。

## 2. `showing` と readable は別である

現状実装でも、track の評価は単に `mode` ではなく、次のような情報で行われている。

- `cuesLength`
- `activeCuesLength`
- current cue text
- cue overlap
- readability snapshot

つまり、実装自身がすでに **「選択されたこと」と「読めること」は別問題**だと扱っている。

このため、成功パターンは「選択後すぐ readable になるケース」、失敗パターンは「`showing` にはなったが cue が来ず、その後 fallback 成否に依存するケース」である。

## 3. 条件判断が分散している

問題を複雑にしている本質は、切り替え経路が 2 つあること以上に、**その判断材料が複数モジュールへ分散していること**である。

少なくとも次の材料が存在する。

- track が見つかったか
- その track が readable か
- 前回 bind と同じ track か
- requested language が変わったか
- monitor が健全か
- force rebind 要求があるか
- recovery が `recover` / `force-rebind` を要求しているか
- native fallback を打つべきか

これらを複数層が別々に解釈すると、同じ現象でも毎回違う経路に入りやすくなり、不安定化する。

***

## 現象整理

## なぜ成功パターンと失敗パターンが分かれるのか

### 成功しやすいパターン

- requested language に一致する track がすぐ見つかる
- `TextTrack` を `showing` にした直後または短時間待機後に cue が読める
- 前回 binding と大きな矛盾がない
- monitor が健全
- native fallback を打たなくても十分動く

### 失敗しやすいパターン

- requested language には合っているように見えるが cue が来ない
- `showing` にはなったが `cuesLength === 0` が続く
- native menu を開いても `menuRoot` / `select` / option 発見に失敗する
- UI 文言や DOM 構造変更で option 一致判定が外れる
- seek / reattach / scene 切り替えと fallback 実行タイミングが競合する
- monitor / recovery / binder / controller が別々に再bind判断を行う

### 要点

成功・失敗の差は、単なる「言語一致判定の精度差」ではなく、**selection・readability・monitor・recovery・native fallback の解釈が一元化されていないこと**にある。

***

## 統合の基本方針

## 方針

**selection result ではなく decision result を単一箇所で返す構成**へ寄せる。

流れは次のように整理する。

1. `track` と `snapshot` を選ぶ
2. 前回 binding 状態と monitor 状態を受け取る
3. recovery 要求を受け取る
4. derived condition を一箇所で作る
5. 最終 action を返す
6. `cue-controller.js` は action 実行だけを担当する

要点は、**「何をすべきか」を `subtitle-sync-controller.js` が返し、他はそれを実行するだけに寄せる**こと。

***

## decision result の正本化

## 中心オブジェクト案

```js
{
  role, // "primary" | "secondary"

  track,
  currentTime,
  snapshot,

  previous: {
    boundTrack,
    boundTrackId,
    requestedLang,
  },

  selection: {
    resolvedTrack,
    selectedTrackId,
    sameTrackRef,
    requestedLanguageChanged,
  },

  monitor: {
    active,
    hasCleanup,
    track,
    sameTrack,
    sameMode,
    healthy,
    stale,
  },

  recovery: {
    requested: false,
    forceRebind: false,
    terminated: false,
    reason: "",
  },

  derived: {
    trackFound,
    readable,
    shouldClear,
    needsReadableWait,
    needsRebind,
    canKeepCurrentBinding,
    needsNativeSelectionFallback,
  },

  action: {
    type:
      "clear" |
      "keep" |
      "wait-and-bind" |
      "bind" |
      "native-fallback-and-wait",
    reason: "",
    requestedMode: "hidden",
  }
}
```

## この形にする意図

- `selection` は「何を選んだか」
- `monitor` は「今の binding が健全か」
- `recovery` は「時間軸観測上、昇格要求があるか」
- `derived` は「現在状態をどう解釈したか」
- `action` は「最終的に何をするか」

これにより、条件の意味とログの意味が分離され、調査しやすくなる。

***

## action の再定義

## 既存 action

### `clear`

対象 lane 用 track が存在しない、または表示を継続すべきでないとき。

### `keep`

今の binding をそのまま維持してよいとき。

### `wait-and-bind`

track はあるが readable でない、または warmup を入れたいとき。

### `bind`

即 bind してよいとき。

## 追加したい action

### `native-fallback-and-wait`

`TextTrack` 上は track が選ばれているが、cue が十分にロードされず、native menu fallback が必要なとき。

```js
action: {
  type: "native-fallback-and-wait",
  reason: "track-showing-but-cues-not-loaded",
  requestedMode: "showing",
}
```

これは、native fallback を adhoc な補助処理ではなく、**明示的な action** として扱うために必要である。

***

## derived condition の再定義

## 基本項目

```js
const trackFound = Boolean(track);
const readable = Boolean(snapshot?.readable);
```

## 差分・健全性

```js
const requestedLanguageChanged = ...;
const sameTrackRef = ...;
const monitorHealthy = ...;
const staleMonitor = ...;
```

## fallback 判定候補

```js
const needsNativeSelectionFallback =
  trackFound &&
  !readable &&
  snapshot?.cuesLength === 0 &&
  !monitorHealthy &&
  recovery?.terminated !== true;
```

この条件は固定値ではなく、ログと実運用で調整する。
単なるロード遅延と、実際の native selection failure を区別するため、待機猶予や試行回数制限を持たせる必要がある。

## 目指す責務分割

| モジュール | 再定義後の主責務 | 持たない責務 |
| :-- | :-- | :-- |
| `modules/subtitle-sync-controller.js` | **字幕 sync decision の正本**。track selection、readability、前回 binding との差分、monitor 状態、recovery 要求を統合し、最終 action を決定する | DOM cleanup、listener attach / cleanup、lane state 保持、実 bind / unbind 実行 |
| `cue-controller.js` | **action 実行と字幕描画 orchestration**。decision を受けて `clear` / `keep` / `wait-and-bind` / `bind` / `native-fallback-and-wait` を実行し、cue を render する | candidate 選別、monitor 健全性の詳細判定、rebind policy のローカル実装 |
| `modules/cue-track-binder.js` | **monitor の実行器・所有者**。listener attach / cleanup、`track.mode` 適用・復元、monitor state 保持 | language selection、readability policy、recovery policy、なぜ rebind するかの判断 |
| `modules/lane-recovery-state.js`（旧 `secondary-track-recovery.js`、Step 15 でリネーム済み） | **lane の継続失敗検出・昇格判定**。runtime missing を時間軸で観測し、`idle` / `recover` / `force-rebind` / `terminated` を返す | track selection、same track 判定、monitor stale 判定、direct bind 実行 |
| `modules/subtitle-recovery-manager.js` | **recovery policy の集約窓口**。both-missing recovery と lane recovery の結果を正規化して返す | DOM / `TextTrack` 保持、listener 操作、track 選定、bind 実行 |
| `modules/playback-session-cleanup.js` | **再生 session 単位の撤収と再入ガード** | track 選択、rebind 判断、recovery 判定、通常時 cue 描画 |
| `content.js` | **Composition Root**。state、controller、binder、recovery manager、cleanup の生成・配線・ライフサイクル入口 | selection、readability、bind / recovery / cleanup の詳細条件 |
| `subtitle-track-resolver.js` | **TextTrack の探索・比較ユーティリティ + native menu 候補探索** | orchestration 全体の最終 policy 決定 |

## 依存方向

```text
content.js
  ├─ cue-controller.js
  ├─ subtitle-sync-controller.js
  ├─ cue-track-binder.js
  ├─ subtitle-recovery-manager.js
  │    └─ lane-recovery-state.js（旧 secondary-track-recovery.js）
  └─ playback-session-cleanup.js

cue-controller.js
  ├─ subtitle-sync-controller.js
  ├─ cue-track-binder.js
  ├─ subtitle-recovery-manager.js
  └─ renderer / scene block APIs

subtitle-sync-controller.js
  └─ subtitle-track-resolver.js
```

理想形では、binder は decision builder を参照せず、recovery モジュールも binder や `TextTrack` 実体を直接参照しない。
これにより、「判定」「実行」「時間軸 recovery」が混ざらなくなる。

***

## ネイティブUIの字幕メニューに影響されない方法

## 1. 依存度を下げる方法

現実的な改善は、native menu を最後の fallback に限定し、基本は `TextTrack` と readability 判定を主軸にすること。

- `TextTrack` 直接切り替え後に readable 化を待つ
- cue が来ない時だけ fallback を使う
- menu open 完了確認を厳密化する
- option 一致判定をテキスト依存から少しでも減らす

## 2. 完全に影響を受けない方法

根本的には、字幕取得から描画までを拡張側で自前実装する必要がある。

- native menu DOM を操作しない
- Apple 側 `select` を触らない
- 字幕ソースを独自取得する
- 独自パース・独自描画する

ただしこれは長期テーマであり、短期 bugfix ではない。

***

## 修正方針

## フェーズA: 観測強化

目的は、成功経路と失敗経路の切り分け。

### 追加したい観測

- `TextTrack` 直接成功か
- native fallback 成功か
- fallback 失敗理由は何か
- `requestedLang`、selected track、`cuesLength`、`activeCuesLength`
- role ごとの成功率差

## フェーズB: native fallback 安定化

- menu open 完了確認を厳密化する
- `select` 検出失敗時の再試行条件を整理する
- option 一致判定を改善する
- pending task 競合を抑える
- fallback 実行回数と timeout を制御する

## フェーズC: native menu 依存縮小

- `TextTrack` + readability wait を主軸にする
- `needsNativeSelectionFallback` が true の時だけ fallback を使う
- primary / secondary の fallback 条件を controller 側で共通化する
- recovery state と readability 判定を接続する

## フェーズD: 完全自前パイプライン検討

- 字幕取得・解析・描画の自前化
- native menu 非依存化
- 別 Issue として長期テーマ化

***

## 現時点の推奨進行順

1. フェーズA で観測を増やす
2. フェーズB で native fallback を安定化する
3. フェーズC で native menu 依存を縮小する
4. フェーズD を別 Issue として切り出す

理由は以下の通り。

- まだ失敗条件の観測が十分でない
- 先に観測を揃えないと修正対象を誤る
- 現行構造のままでも安定化できる余地が大きい
- 根本解決案は別テーマとして扱った方が設計を壊しにくい

## 命名見直しメモ

**(Step 15 で対応済み)** `secondary-track-recovery.js` は `modules/lane-recovery-state.js` へリネームした。

対応内容の要約:

- ファイル名: `secondary-track-recovery.js` → `lane-recovery-state.js`
- 生成関数名: `createSecondaryTrackRecovery` → `createLaneRecoveryState`
- content.js 側の変数名: `secondaryTrackRecovery` → `laneRecoveryState`
- `subtitle-recovery-manager.js` への DI プロパティ名: `secondaryTrackRecovery` → `laneRecoveryState`
- 公開メソッド名（`laneStates` / `evaluateSecondaryRecovery` / `resetSecondaryRecoveryLane` 等）は責務整理と decision 正本化を優先し、今回は変更していない
- テストファイル: `tests/secondary-track-recovery.test.js` → `tests/lane-recovery-state.test.js`

改名の理由は、このモジュールが名前に反して primary / secondary の両 lane state を持っており、実態に合わせて中立的な名前へ揃える必要があったため。
